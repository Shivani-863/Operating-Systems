Introduction

👋 Hello, Future OS Expert!

Imagine you just walked into a bustling restaurant kitchen. There are chefs (programs), ovens (hardware), waiters running around, ingredients in storage... Someone has to manage all of this chaos — deciding which chef uses the oven next, making sure no one crashes into each other, and keeping the pantry organized.

That someone is the Operating System (OS).

🍳 Real-World Analogy

The OS is like the head chef / kitchen manager of a restaurant. Programs are the recipes. The CPU is the stove. RAM is the counter space. The disk is the pantry. The OS decides who cooks, when, and how much counter space they get.

What Exactly Is an Operating System?

An OS is a system software that sits between your hardware (the physical machine) and your applications (Chrome, Word, games). It provides three key services:

  • Resource Management — shares CPU, RAM, and disk among many programs
  • Abstraction — hides messy hardware details behind clean, simple interfaces
  • Protection — makes sure one program can't crash or spy on another
📌 Key Examples
Windows, macOS, Linux, Android, iOS — these are all Operating Systems. They're different in style but share the same core job.

Topic 01

🏗️ OS Architecture & System Calls

Layers of a Computer System

A computer system is organized in layers, like an onion. The hardware is at the center, and user applications are on the outside:

┌─────────────────────────────────┐ │ User Applications │ ← Chrome, Word, your code ├─────────────────────────────────┤ │ System Libraries / APIs │ ← printf(), malloc() ├─────────────────────────────────┤ │ Operating System Kernel │ ← The heart of the OS ├─────────────────────────────────┤ │ Hardware │ ← CPU, RAM, Disk, GPU └─────────────────────────────────┘

Kernel vs. User Mode

The CPU operates in two privilege modes:

  • Kernel Mode (Privileged): The OS runs here. It can access anything — memory, hardware, all instructions. Full power.
  • User Mode (Restricted): Your applications run here. They cannot directly touch hardware. They must "ask" the OS politely.
🏦 Analogy

Think of a bank. Customers (user mode) can't go into the vault themselves. They have to ask a teller (the OS, running in kernel mode) to do it for them. The teller verifies the request and acts on it safely.

System Calls — The Bridge

A system call is how a user program requests a service from the OS kernel. It's the only legal gateway from user mode to kernel mode.

CategoryExample System CallsWhat They Do
Process Controlfork(), exec(), exit()Create, run, terminate processes
File Managementopen(), read(), write(), close()Work with files
Device Managementioctl(), read(), write()Communicate with hardware
Informationgetpid(), time()Get system info
Communicationpipe(), socket()Talk between processes

Types of OS Architectures

  • Monolithic Kernel: Everything (file system, drivers, scheduler) runs in one big kernel space. Fast, but risky — a bug can crash everything. Example: Linux.
  • Microkernel: Only the absolute minimum (IPC, basic scheduling) runs in kernel mode. Everything else runs in user space. More stable, but slower due to context switches. Example: Minix.
  • Hybrid Kernel: Mix of both. Example: Windows NT, macOS XNU.
  • Exokernel: Gives hardware access directly to applications — extremely minimal abstraction. Research-oriented.
Topic 02

⚙️ Processes, PCB & Threads

What Is a Process?

A process is a program in execution. A program is a passive file sitting on your disk (like a recipe in a book). A process is that program actively running, using CPU and memory (like a chef actually cooking that recipe).

Every process has its own:

  • Code segment: The actual instructions
  • Data segment: Global variables
  • Heap: Dynamic memory (malloc'd data)
  • Stack: Function calls, local variables

Process States — The Life of a Process

┌──────────────────────────────────────────────────┐ │ │ New ──→ Ready ──→ (Scheduler picks it) ──→ Running ↑ │ │ (I/O done) │ Waiting ←──────────────────────── (Needs I/O) │ Terminated
  • New: Process is being created
  • Ready: Waiting for CPU time
  • Running: Currently executing on CPU
  • Waiting (Blocked): Waiting for I/O or an event
  • Terminated: Finished execution

Process Control Block (PCB) — The Process's ID Card

The OS keeps a data structure for each process called the PCB. Think of it as the process's official government file.

PCB FieldWhat It Stores
Process ID (PID)Unique identifier for the process
Process StateNew, Ready, Running, Waiting, Terminated
Program Counter (PC)Address of the next instruction to execute
CPU RegistersAll register values — saved during context switch
Memory LimitsBase and limit registers for memory boundaries
Open FilesList of files currently open
Scheduling InfoPriority, burst time, arrival time

Context Switching

When the OS switches the CPU from one process to another, it must save the current process's PCB and load the next process's PCB. This is called a context switch. It has overhead — the CPU does zero useful work during a context switch.

Threads — Lightweight Processes

A thread is a unit of execution within a process. A single process can have multiple threads, and they all share the process's memory (code, data, heap). Each thread has its own stack and program counter.

🍽️ Analogy

A process is a restaurant. Threads are the individual waiters. They all share the same kitchen (memory), menu (code), and customer list (data), but each waiter independently takes orders (has their own stack/PC).

FeatureProcessThread
MemorySeparate address spaceShared with parent process
Creation overheadHighLow
CommunicationComplex (IPC needed)Easy (shared memory)
Crash impactIsolatedCan crash whole process
⚠️ Important
Threads are faster to create and communicate, but they're more dangerous — a bug in one thread can corrupt shared memory for all other threads in the same process.
Topic 03

⏱️ CPU Scheduling Algorithms

The CPU Scheduler decides which process from the Ready Queue gets the CPU next. This is one of the most critical OS decisions — bad scheduling = slow, unresponsive system.

Key Terms First

TermMeaning
Burst Time (BT)Time the process needs on the CPU
Arrival Time (AT)When the process enters the ready queue
Completion Time (CT)When the process finishes
Turnaround Time (TAT)CT − AT (total time in system)
Waiting Time (WT)TAT − BT (time spent waiting)
Response TimeTime from arrival to first CPU access

1. FCFS — First Come, First Served

The simplest algorithm. Whoever arrives first gets the CPU first. Non-preemptive — once a process starts, it runs to completion.

⚠️ Convoy Effect
If a long process arrives first, all short processes wait a long time. This is called the Convoy Effect — the biggest problem with FCFS.

2. SJF — Shortest Job First

The process with the shortest burst time goes next. This minimizes average waiting time — it's actually optimal for average WT. But it can cause starvation — long processes may never run if short ones keep arriving. Non-preemptive.

3. SRTF — Shortest Remaining Time First

The preemptive version of SJF. If a new process arrives with a shorter remaining burst than the current process, the current process is preempted (kicked off the CPU). Most optimal for average WT, but complex to implement.

4. Round Robin (RR)

Each process gets a fixed time quantum (q). After q units, if not done, it's preempted and sent to the back of the ready queue. This is the most widely used algorithm in real systems because it's fair and gives good response time.

📌 Choosing the Right Quantum
Too small a quantum → too many context switches, high overhead. Too large → degrades to FCFS. The art is in finding the sweet spot.

5. Priority Scheduling

Each process has a priority number. The CPU always goes to the highest-priority process. Can be preemptive or non-preemptive.

Problem: Starvation. Low-priority processes may never run. Solution: Aging — gradually increase the priority of waiting processes over time.

Scheduling Algorithm Comparison

AlgorithmTypeBest ForMain Problem
FCFSNon-preemptiveSimple batch systemsConvoy Effect
SJFNon-preemptiveBatch, known burst timesStarvation
SRTFPreemptiveMin. avg. waiting timeStarvation, overhead
Round RobinPreemptiveTime-sharing, interactiveHigh context switches
PriorityBothReal-time systemsStarvation
Topic 04

🔒 Process Synchronization

The Problem: Race Conditions

When multiple processes/threads access shared data concurrently, and the outcome depends on the exact timing of execution, we have a race condition. The result is unpredictable and often wrong.

🏦 Analogy

Imagine two people simultaneously withdrawing ₹1000 from a bank account that has only ₹1000. If both check the balance at the same time and both see ₹1000, both withdraw successfully — leaving the account at −₹1000. That's a race condition!

The Critical Section Problem

A Critical Section is the piece of code that accesses shared resources. At any given time, only one process should be in its critical section.

Any solution to the critical section problem must satisfy:

  • Mutual Exclusion: Only one process at a time in the critical section
  • Progress: If no one is in the critical section, a waiting process must get in eventually — no unnecessary blocking
  • Bounded Waiting: A process must be guaranteed to enter the critical section in a finite time — no starvation

Mutex (Mutual Exclusion Lock)

A mutex is a simple locking mechanism. A process acquires the lock before the critical section and releases it after. Only the owner can release a mutex.

mutex.lock(); // Acquire lock — waits if locked // ← Critical Section → shared_counter++; mutex.unlock(); // Release lock

Semaphores — The Traffic Light

A semaphore is a more powerful synchronization tool. It's an integer variable with two atomic operations:

  • wait(S) / P(S): Decrements S. If S becomes negative, the process sleeps.
  • signal(S) / V(S): Increments S. If any process is sleeping, wake one up.
TypeInitial ValueUse Case
Binary Semaphore0 or 1Works like a mutex
Counting SemaphoreN (any non-negative)Manage a pool of N resources (e.g., N printers)

Classic Synchronization Problems

  • Producer-Consumer Problem: Producer adds to a buffer; Consumer removes from it. Must synchronize so producer doesn't overfill and consumer doesn't read from empty buffer.
  • Dining Philosophers Problem: 5 philosophers, 5 chopsticks, must pick up 2 adjacent chopsticks to eat. Demonstrates deadlock and resource allocation challenges.
  • Readers-Writers Problem: Multiple readers can read simultaneously, but a writer needs exclusive access. Balancing fairness is the challenge.
Topic 05

☠️ Deadlocks

What Is a Deadlock?

A deadlock is a state where a set of processes are stuck forever, each waiting for a resource held by another process in the same set. Nobody can move. Nothing gets done.

🚗 Analogy

Imagine a single-lane bridge. Car A is on the bridge going east, and Car B is on it going west. Neither can move forward, neither wants to back up. They're deadlocked.

Coffman's 4 Necessary Conditions

A deadlock can occur only if all four of these conditions hold simultaneously:

  1. Mutual Exclusion: Resources are non-shareable (only one process can use a resource at a time)
  2. Hold and Wait: A process holds at least one resource and is waiting to acquire others held by other processes
  3. No Preemption: Resources cannot be forcibly taken away — only released voluntarily
  4. Circular Wait: P1 waits for P2, P2 waits for P3, P3 waits for P1 — a cycle!
📌 Memory Trick
M-H-N-C → "My Hamster Needs Cheese" → Mutual exclusion, Hold & wait, No preemption, Circular wait.

Deadlock Prevention

Prevent deadlock by eliminating at least one of the four conditions:

  • Deny Mutual Exclusion — not always possible (printers truly need exclusion)
  • Deny Hold & Wait — require a process to request ALL resources at once before starting
  • Allow Preemption — if a process can't get what it needs, take back its current resources
  • Deny Circular Wait — impose an ordering on all resource types; processes must request in order

Deadlock Avoidance — The Banker's Algorithm

Rather than preventing, we avoid deadlock by only granting resource requests if the resulting state is safe.

A safe state means there exists a sequence (called a safe sequence) in which every process can get its maximum resources and finish. If no such sequence exists, it's an unsafe state.

The Banker's Algorithm (by Dijkstra) checks safety before every allocation:

  • Let Need[i] = Max[i] − Allocation[i] for each process
  • Set Work = Available and Finish[i] = false for all i
  • Find an i such that Finish[i] == false AND Need[i] ≤ Work
  • If found: Work = Work + Allocation[i], Finish[i] = true, go to step 3
  • If all Finish[i] == true → Safe State! Otherwise → Unsafe State.

Deadlock Detection & Recovery

If we don't prevent or avoid deadlocks, we need to detect them and recover:

  • Detection: Use a Resource Allocation Graph (RAG). A cycle in the RAG with single-instance resources means deadlock.
  • Recovery Options:
    • Terminate one or all deadlocked processes (lose their work)
    • Preempt resources from a process (and roll it back)
Topic 06

🧩 Memory Management

The OS must allocate RAM to processes efficiently while protecting each process's memory from others.

Contiguous Memory Allocation

Early systems gave each process one contiguous (unbroken) block of physical memory.

Fixed Partitioning: RAM is divided into fixed-size partitions. Simple, but causes internal fragmentation — unused space inside a partition.

Dynamic Partitioning: Partitions sized exactly to the process. Causes external fragmentation — free memory scattered in small chunks that can't be used. Solved by compaction (shuffling processes together).

Paging — The Great Solution

Paging breaks physical memory into fixed-size frames and logical memory into same-size pages. A process's pages can be scattered across any available frames — no need for contiguous allocation!

📚 Analogy

Imagine your notes are in loose pages. You can store page 1 in drawer A, page 2 in drawer C, page 3 in drawer B. As long as you have a table of contents (page table) telling you where each page is, you can reconstruct the full notes.

A Page Table maps logical page numbers to physical frame numbers. The CPU uses a logical address (page number, offset) which the Memory Management Unit (MMU) translates to a physical address.

✅ Advantage
Paging eliminates external fragmentation! Pages fit perfectly into frames. Only minor internal fragmentation in the last page of a process.

TLB (Translation Lookaside Buffer): A tiny, super-fast cache for recent page table entries. Instead of going to the page table in RAM every time (slow!), we first check the TLB. A TLB hit speeds up address translation dramatically.

Segmentation

Segmentation divides a process's memory into variable-size segments based on logical divisions: code segment, data segment, stack segment, heap segment. Each segment has a base address and a limit.

FeaturePagingSegmentation
Division basisFixed-size pagesLogical units (code, data, stack)
External fragmentationNoneYes (variable sizes)
Internal fragmentationYes (last page)None
User visibilityHiddenVisible to programmer

Modern systems often use Segmentation with Paging (e.g., x86) — each segment is divided into pages, combining the benefits of both.

Topic 07

💫 Virtual Memory

Virtual Memory is one of the cleverest ideas in computer science. It gives each process the illusion that it has a huge, private address space — even if physical RAM is small.

📖 Analogy

Imagine you're studying from a 1000-page textbook but your desk only fits 10 pages at a time. You keep swapping pages: you put the pages you're done with back in the book and bring out the new ones you need. Virtual memory works exactly like this — your desk is RAM, the book is disk.

Demand Paging

With demand paging, pages are loaded into RAM only when needed (on demand), not all at once. When a process accesses a page that isn't in RAM, a page fault occurs:

  • CPU accesses an address; MMU checks the page table
  • Page table shows the page is not present (valid bit = 0) → Page Fault!
  • OS traps to the page fault handler
  • OS finds a free frame (or evicts one) and loads the page from disk
  • Update the page table with the new frame number, valid bit = 1
  • Restart the faulting instruction

Page Replacement Algorithms

When RAM is full and a page fault occurs, the OS must choose a victim page to evict (write back to disk). The choice matters — bad choices cause excessive page faults (thrashing).

1. FIFO — First In, First Out

Evict the page that has been in memory the longest. Simple, but not always smart — an old page might still be frequently used. FIFO can suffer from Belady's Anomaly: adding more frames can sometimes cause more page faults!

2. LRU — Least Recently Used

Evict the page that was least recently accessed. This is based on locality of reference — if a page hasn't been used in a while, it probably won't be needed soon. LRU is generally excellent but expensive to implement perfectly (need timestamps).

3. Optimal (OPT / Bélády's Algorithm)

Evict the page that won't be used for the longest time in the future. This is theoretically the best possible algorithm — guaranteed minimum page faults. But it's impossible to implement in practice (we can't predict the future). It's used as a benchmark to compare other algorithms.

AlgorithmEvictsPage FaultsPractical?
FIFOOldest loaded pageHighYes (easy)
LRULeast recently usedLowYes (with approximation)
OptimalNot used longest in futureMinimum possibleNo (theoretical)

Thrashing

Thrashing occurs when a process spends more time page-faulting (swapping pages in and out) than actually executing. The CPU utilization drops sharply. Solution: reduce the degree of multiprogramming (run fewer processes) or increase RAM.

Topic 08

📁 File Systems & Directory Structure

The file system is how the OS organizes data on persistent storage (disk, SSD). It provides a friendly abstraction (files and folders) over raw disk blocks.

What Is a File?

A file is a named collection of related data. From the OS perspective, it's a sequence of bytes. The OS manages files through metadata stored in a structure called an inode (index node).

Inode contains: file size, owner, permissions, timestamps, and pointers to the actual data blocks on disk. It does not contain the file name (that lives in the directory).

Directory Structures

StructureDescriptionLimitation
Single-LevelAll files in one directoryNo organization, naming conflicts
Two-LevelOne directory per userNo sharing between users
Tree-StructuredHierarchical, like Unix/WindowsHard to share files across branches
Acyclic GraphAllows shared subdirectories (symlinks)Dangling pointers on deletion
General GraphAllows cyclesNeed garbage collection

File Allocation Methods

How are file blocks arranged on disk?

  • Contiguous Allocation: All blocks of a file stored sequentially. Fast sequential read, but causes external fragmentation and can't easily grow files.
  • Linked Allocation: Each block has a pointer to the next. No fragmentation, files can grow easily. But slow for random access (must follow the chain), and a broken pointer corrupts everything.
  • Indexed Allocation: A special index block holds pointers to all the file's blocks. Good random access, no external fragmentation. Used by Unix inodes with direct/indirect block pointers.

File System Examples

  • FAT (File Allocation Table): Old Windows, USB drives. Simple linked allocation using a table.
  • NTFS: Modern Windows. Journaling, permissions, large file support.
  • ext4: Default Linux filesystem. Indexed allocation, journaling, extents.
Topic 09

💿 Disk Scheduling Algorithms

Traditional Hard Disk Drives (HDDs) have a read/write head that moves across spinning platters. The time to access data = Seek Time (moving head to right track) + Rotational Latency + Transfer Time. Seek time dominates, so we minimize total head movement.

FCFS — First Come, First Served

Process requests in arrival order. Fair, but head movement can be huge. Good for light disk loads.

SSTF — Shortest Seek Time First

Always service the request closest to the current head position. Minimizes total movement better than FCFS. Problem: starvation — requests far from the head may never be served.

SCAN (Elevator Algorithm)

Head moves in one direction, servicing all requests along the way, then reverses. Like an elevator — goes up servicing floors, then comes back down. No starvation. Slight unfairness to requests just behind the head after a reversal.

C-SCAN (Circular SCAN)

Like SCAN, but after reaching one end, the head immediately jumps back to the beginning without servicing on the way back. Provides more uniform wait times. C-LOOK is the practical version — head only goes as far as the last request in each direction, not to the physical end of disk.

AlgorithmStrategyStarvation?Best When
FCFSArrival orderNoLight load
SSTFNearest firstYesBurst performance
SCANElevatorNoHeavy, uniform load
C-SCANOne-direction elevatorNoUniform response time
C-LOOKPractical C-SCANNoMost real systems
✅ Note on SSDs
SSDs have no moving parts, so seek time is negligible. Disk scheduling algorithms are mostly irrelevant for SSDs — the OS uses simpler queuing for them.
