Module 1: Basics of Contemporary OS & User Management

Part 1: Operating System Fundamentals

An Operating System (OS) is the foundational system software that manages computer hardware, software resources, and provides common services for computer programs. It acts as an intermediary between the user of a computer and the computer hardware.

The OS serves two primary functions:

  • Resource Allocator: It manages all system resources (CPU time, memory space, file storage space, I/O devices) and allocates them to specific programs and users as necessary for efficient and fair operation.
  • Control Program: It controls the execution of user programs to prevent errors and improper use of the computer, ensuring that a malfunctioning program cannot crash the entire system or access unauthorized data.

The Kernel vs. User Space

Modern operating systems divide system memory into two distinct zones to ensure stability and security:

  • Kernel Space: A strictly reserved memory area for running the core of the OS (the Kernel), hardware drivers, and core extensions. Code running here has unrestricted access to the underlying hardware.
  • User Space: A restricted memory area where standard application software (e.g., web browsers, word processors) runs. Applications in user space cannot access hardware directly; they must communicate with the kernel through a "System Call Interface."

Part 2: Contemporary OS Architectures

Linux Architecture (The Monolithic Kernel)

Linux utilizes a Monolithic Kernel design. In this architecture, all core OS services (process management, memory management, file systems, device drivers) execute in the same memory space (Kernel Space).

  • Advantages: Communication between different OS components is extremely fast and efficient because they share the same memory space.
  • Disadvantages: If a single component (like a graphics driver) crashes, it can potentially bring down the entire system (resulting in a "Kernel Panic").
  • Structure: Hardware Level → Kernel Level (monolithic block) → System Call Interface → User Space (Applications)

Windows Architecture (The Hybrid Kernel)

Modern Windows systems (based on the Windows NT architecture) utilize a Hybrid Kernel (often described as a modified microkernel). It attempts to combine the stability of a microkernel with the performance of a monolithic kernel.

  • Design Philosophy: Core OS components are kept in kernel space, but many non-critical services (like the user interface or specific environmental subsystems) are moved into user space.
  • Hardware Abstraction Layer (HAL): Windows features a unique layer called the HAL. It sits directly above the hardware and hides the specific hardware differences from the rest of the OS. This allows Windows to run on vastly different hardware configurations without needing core rewrites.
  • Advantages: High stability. A crash in a user-mode subsystem does not crash the core OS.

Part 3: User Management Systems

Linux User Management

In Linux, "everything is a file," and security is fundamentally tied to file ownership and permissions.

  • Root User: Absolute administrator. Bypasses permission checks. UID = 0.
  • UIDs/GIDs: Numeric identifiers for users and groups (not names).
  • Permissions: Owner, Group, Others with Read/Write/Execute rights.

Windows User Management

Object-based security model. Every resource (file, printer, process) is an object with security descriptor.

  • SIDs: Unique alphanumeric Security Identifiers (not simple numeric UIDs).
  • UAC: User Account Control strips admin privileges from standard tasks.

Key Definitions

OS: Intermediary managing hardware and providing application services.

Kernel: Central OS module. Loads first, stays in memory, controls hardware.

Monolithic: All services in kernel space for speed.

Hybrid: Core services in kernel, non-essential in user space for stability.

HAL: Hardware Abstraction Layer hiding hardware complexity.

UID: User Identifier - numeric user ID in Unix/Linux.

SID: Security Identifier - unique Windows user/group/computer identifier.

Key Formulas - Linux Octal Permissions

Values: r=4, w=2, x=1

Formula: Permission Digit = r(4) + w(2) + x(1) for each category (Owner, Group, Others)

Example: Owner full (7) + Group rx (5) + Others r (4) = 754 permission

Module 2: System Calls, Process Concept, and Threads

Part 1: System Calls (The Gateway to the Kernel)

User Space applications cannot directly interact with hardware. System Calls are the mechanism for requesting kernel services.

How System Calls Work (Trap Mechanism):

  1. Application calls API function (e.g., printf in C)
  2. API triggers software interrupt (Trap/Exception)
  3. CPU switches from User Mode (1) to Kernel Mode (0)
  4. OS looks up request in System Call Table by system call number
  5. Kernel executes operation securely
  6. CPU returns to User Mode with control back to application

Major System Call Categories:

  • Process Control: fork(), exit(), wait()
  • File Management: open(), read(), write(), close()
  • Device Management: Hardware access requests/releases
  • Information: getpid(), time()
  • Communication: Pipes, network sockets

Part 2: The Process Concept

Program: Passive entity (recipe in a book). Process: Active entity (chef cooking). Process = Program in execution.

Process Memory Layout

  • Text: Compiled code
  • Data: Global/static variables
  • Heap: Dynamic memory (grows upward)
  • Stack: Parameters, return addresses, locals (grows downward)

PCB (Process Control Block)

Data structure containing: State, Program Counter, Registers, Scheduling Info, Memory Info, I/O Status

Process State Lifecycle

  • New: Being created
  • Ready: In memory, waiting for CPU
  • Running: Executing on CPU
  • Waiting: Waiting for event (I/O, input)
  • Terminated: Finished

Part 3: Threads (Lightweight Processes)

Multiple execution paths within single process. Threads share code/data but have private stack/registers.

Thread Types

  • User-Level: Managed by library in user space. Fast but if one blocks, whole process blocks.
  • Kernel-Level: Managed by OS. Slower but independent blocking.

Key Definitions

System Call: Interface for apps to request OS kernel services.

Trap: Software interrupt switching user mode to kernel mode.

Process: Program in execution, loaded in main memory.

PCB: OS data structure storing process vital information.

Context Switch: Save current process state, load next process state.

Thread: Basic CPU unit sharing process code/data, own stack/registers.

Multithreading: Multiple concurrent execution paths in single process.

Key Formulas - fork() Process Creation

Total Processes: 2^n (n = number of fork() calls)

Child Processes: 2^n - 1

Example: Three fork() → 8 total, 7 new children

Module 3: Task Scheduling (CPU Scheduling Algorithms)

Part 1: Core Concept

With multiple processes in Ready Queue, OS must decide which process gets CPU next. This is CPU Scheduling managed by Short-Term Scheduler.

Preemptive vs. Non-Preemptive

  • Non-Preemptive: Process keeps CPU until voluntarily releasing.
  • Preemptive: OS can forcefully interrupt and return to Ready Queue.

Part 2: Scheduling Criteria

  • CPU Utilization: Keep CPU busy (target 100%)
  • Throughput: Processes completed per time unit
  • Turnaround Time: Arrival to completion
  • Waiting Time: Time in Ready Queue
  • Response Time: Until first CPU allocation

Part 3: Scheduling Algorithms

1. FCFS (First-Come, First-Served)

Non-Preemptive. Process arriving first gets CPU first. Problem: Convoy Effect - short processes stuck behind long ones.

2. SJF (Shortest Job First)

Non-Preemptive. Smallest burst time gets CPU. Minimum average wait time BUT causes starvation.

3. SRTF (Shortest Remaining Time First)

Preemptive SJF. If new process shorter than remaining current process time, preempt.

4. Round Robin (RR)

Preemptive. Fixed time quantum per process. Goes to back of queue when quantum expires. Fair allocation.

5. Priority Scheduling

Highest priority gets CPU. Can be preemptive or non-preemptive. Problem: starvation. Solution: aging (boost waiting process priority).

Key Definitions

Burst Time: Time process requires CPU

Arrival Time: When enters Ready Queue

Completion Time: Execution finish

Time Quantum: Max RR time slice

Convoy Effect: FCFS short stuck behind long

Starvation: Process never gets CPU

Aging: Boost waiting process priority

Gantt Chart: Scheduling timeline visualization

Key Formulas

TAT: Turnaround Time = CT - AT

WT: Waiting Time = TAT - BT

RT: Response Time = First Allocation - AT

Average TAT: Σ TAT_i / n

Average WT: Σ WT_i / n

CPU Utilization: (Total execution / Total time) × 100%

Module 4: Inter-Process Communication (IPC) & Synchronization

Part 1: IPC

Processes run in isolated memory. When needing to cooperate, they use IPC mechanisms.

IPC Models

  • Shared Memory: OS creates shared region. Fast but coordination needed.
  • Message Passing: Via OS kernel send()/receive(). Slower but safer.

Part 2: Critical Section Problem

When multiple processes share data concurrently, race conditions occur (outcome depends on unpredictable timing).

Three Critical Section Rules

  1. Mutual Exclusion: Only one process in critical section simultaneously
  2. Progress: Waiting process must eventually enter
  3. Bounded Waiting: Limit on processes cutting in line (no starvation)

Part 3: Synchronization Tools

Mutex Locks

Binary lock. acquire() to enter, release() to exit. If locked, process sleeps.

Semaphores

Integer S with atomic wait()/signal() operations.

  • wait(S): If S>0 decrement, else sleep
  • signal(S): Increment S, wake sleeping process
  • Binary: 0/1 (like Mutex)
  • Counting: Any integer (multiple resources)

Classic Problems

  • Producer-Consumer: Sync producer data creation and consumer consumption
  • Reader-Writer: Readers concurrent, writer exclusive

Key Definitions

IPC: Isolated process data sharing mechanisms

Race Condition: Outcome depends on unpredictable execution timing

Critical Section: Code accessing/modifying shared data

Mutex: Mutual exclusion lock

Semaphore: Integer for process synchronization

Key Formulas - Semaphore

Current Value: Initial + Signals - Waits

Blocked Processes: If negative, absolute value = blocked count

Example: S=5, 12 waits, 4 signals → 5+4-12=-3. All 5 resources used, 3 waiting.

Module 5: Deadlocks and Resource Allocations

Part 1: Deadlock Concept

System state where processes permanently blocked. Each holds resource, waits for another's resource. Circular dependency.

Coffman Conditions (All 4 Required)

  1. Mutual Exclusion: Non-shareable resource
  2. Hold and Wait: Holding resource while waiting for another
  3. No Preemption: Can't forcefully take resource
  4. Circular Wait: Circular resource requesting chain

Break any ONE condition = deadlock impossible

Part 2: Resource Allocation Graphs (RAG)

Circles=Processes, Squares=Resources. Arrows: Request Edge (P→R wanting), Assignment Edge (R→P holding).

  • No cycles = NO deadlock
  • Cycle + single resource = DEADLOCK
  • Cycle + multiple resources = might deadlock

Part 3: Deadlock Handling Strategies

1. Ostrich Algorithm

Ignore deadlocks. If occurs, user reboots. Used by Windows, Linux, macOS!

2. Prevention

Structure system so one Coffman condition impossible. Example: Number resources, require increasing order requests.

3. Avoidance (Banker's Algorithm)

Before granting resource, simulate. Only grant if leads to "Safe State" (all processes finishable).

4. Detection & Recovery

Run normally, scan for cycles periodically. If detected, abort/preempt appropriately.

Key Definitions

Deadlock: Processes unable to proceed waiting for each other's resources

RAG: Directed graph of process resource holdings/requests

Safe State: At least one execution sequence all finish without deadlock

Unsafe State: Deadlock could occur (no guarantee)

Banker's Algorithm: Deadlock avoidance via simulation

Key Formulas - Banker's Algorithm

Need Matrix: Need[i,j] = Max[i,j] - Allocation[i,j]

Safety: If Need_i ≤ Available → can execute

Release: New Available = Current + Allocation_i

Module 6: Memory Management (Paging, Segmentation, Virtual Memory)

Part 1: Memory Basics

CPU fast, no storage. Disk massive, slow. RAM between them.

Golden Rule: Load program from disk to RAM before CPU can execute.

Logical vs. Physical Addresses

  • Logical (Virtual): CPU-generated. Program thinks it owns everything from 0.
  • Physical: Actual RAM hardware location.
  • MMU: Hardware translating virtual to physical instantly.

Part 2: Contiguous Allocation Problems

  • Internal Fragmentation: Space inside allocated block wasted
  • External Fragmentation: Free space fragmented, can't fit process

Part 3: Non-Contiguous Solutions

Paging

Chop process into Pages, RAM into Frames (same size). Any page fits any frame. Page Table maps pages to frames. Eliminates external fragmentation!

Segmentation

Chop into logical sections (code, data, stack). Segment Table tracks base and limit.

Part 4: Virtual Memory & Demand Paging

Virtual Memory: Illusion of massive memory using disk.

Demand Paging: Load pages only when CPU demands.

Page Fault: CPU accesses page not in RAM. OS fetches from disk, loads to frame, restarts process.

Part 5: Page Replacement Algorithms

FIFO

Evict oldest page. Problem: Belady's Anomaly (more frames = more faults!).

LRU (Least Recently Used)

Evict unused longest. Excellent performance. No Belady's Anomaly.

OPT (Optimal)

Evict page unused longest in future. Requires time machine! Used mathematically.

Part 6: TLB (Translation Lookaside Buffer)

Problem: Page Table in RAM. CPU needs 2 RAM accesses (1 for table, 1 for data).

Solution: TLB is tiny fast cache in MMU storing recent translations.

  • Hit: Found instantly (1 access)
  • Miss: Access page table (2 accesses)

Part 7: Thrashing & Working Set

Thrashing: More time swapping than executing.

Cause: Too many processes, not enough frames.

Solution: Only run process if free RAM ≥ working set size.

Key Definitions

MMU: Virtual-to-physical address mapping hardware

Page: Fixed logical memory block

Frame: Fixed physical RAM block

Page Table: Maps logical pages to physical frames

Page Fault: Program accesses page not in RAM

Thrashing: Excessive page swapping

Belady's Anomaly: More frames → more faults (FIFO only)

Key Formulas

Pages Count: Address Space / Page Size

Bit-based Pages: If address m bits, page n bits: Pages = 2^(m-n)

EAT (Demand): (1-p)×m + p×pf (p=fault rate, m=access time, pf=fault service time)

EAT with TLB: H×(c+m) + (1-H)×(c+2m) (c=TLB time, H=hit ratio)

Module 7: Disk Management, I/O, and File Systems

Part 1: I/O Management

Computers have many slow devices. If CPU managed them, would waste time waiting.

I/O Components

  • Device Drivers: Software translator between kernel and hardware
  • Device Controllers: Hardware microchip receiving commands

I/O Communication Methods

  • Polling: CPU asks repeatedly "ready?" Wasteful.
  • Interrupt-Driven: Device interrupts when done. CPU does other work.
  • DMA: Hardware directly moves data to RAM. CPU completely free.

Part 2: Hard Disk Components

  • Platters: Spinning magnetic disks
  • Tracks: Concentric circles (like tree rings)
  • Sectors: Track slices (usually 512 bytes)
  • Cylinders: Same track vertical stack
  • Head: Robotic arm reading/writing

Three Delays

  1. Seek: Arm moving (slowest!)
  2. Rotational Latency: Platter spinning
  3. Transfer: Reading data

Part 3: Disk Scheduling Algorithms

FCFS

Serve in arrival order. Wildly inefficient.

SSTF

Go to nearest track. Can starve outer cylinders.

SCAN

Like elevator - sweep one direction, reverse at end. Fair.

C-SCAN

Sweep one direction, jump to start. More uniform wait times.

LOOK/C-LOOK

Smarter - only go as far as last request, then reverse/jump.

Part 4: File Systems

Directory Structures

  • Single-Level: One folder all files
  • Two-Level: Master + per-user folders
  • Tree: Nested folders from root

File Allocation

  • Contiguous: Single block. Fast but fragmentation.
  • Linked: Scattered with pointers. Bad random access.
  • Indexed (Inode): Master index with all addresses. Best!

Key Definitions

Spooling: Jobs in buffer for device processing

DMA: Hardware direct memory access

Seek Time: Arm movement time

Latency: Rotation waiting time

Inode: Linux file structure with addresses

Key Formulas

Access Time: Seek + Latency + Transfer

Head Movement: Σ |Destination - Position|

Avg Latency: Usually 0.5 × rotation time

Module 8: Protection, Security, and Real-Time Systems

Part 1: Protection vs. Security

  • Protection: Internal - Process A can't write Process B's memory
  • Security: External - Defense against malware and attackers

Part 2: Access Matrix Model

Track who accesses what. Rows=Users/Processes, Columns=Resources, Cells=Permissions.

Implementation

  • ACLs: Permission list per file. "User A read, User B write."
  • Capability Lists: Permission keychain per process.

Part 3: System Threats

Malware Types

  • Virus: Attaches to program. Human action spreads.
  • Worm: Standalone, self-replicating. No host, no human needed.
  • Trojan: Disguised useful software with hidden payload.
  • Logic Bomb: Dormant until condition met, then detonates.

Part 4: Real-Time Operating Systems

Goal: Complete tasks within strict deadlines (not fairness/throughput).

Hard Real-Time

Missing deadline = catastrophic failure/loss of life. Pacemakers, airbags, rockets.

Soft Real-Time

Missing deadline = degraded performance (not critical). Video streaming, gaming.

Key Definitions

Protection: Internal process isolation

Security: External threat defense

Authentication: Verify who user is

Authorization: Verify what allowed

RTOS: Real-Time OS with timing guarantees

Additional Topics

Boot Process and System Initialization

Sequence: Firmware (BIOS/UEFI) → Bootloader → Kernel Loading → Hardware/Driver Init → System Processes.

Interrupts and Exception Handling

Interrupts: Hardware/software signals pausing CPU, transferring to kernel.

Exceptions: Synchronous errors (divide-by-zero, page faults).

Kernel Structures and System Calls

Transition: User space → software interrupt → trap handler → kernel space → system call table → execution → return.

Extra Practice MCQs

Question 1

Which is NOT a valid CPU scheduling metric?

  • A) Turnaround Time
  • B) Waiting Time
  • C) Context Switching Time
  • D) Program Source Code Size

Answer: D - Source code size unrelated to scheduling.

Question 2

In paging, what translates logical pages to physical frames?

  • A) TLB
  • B) Page Table
  • C) Inode Table
  • D) Free List

Answer: B - Page Table is primary. TLB is cache.

Question 3

HAL in Windows isolates what?

  • A) User passwords
  • B) Device-specific hardware details
  • C) CPU scheduling
  • D) Cloud connectivity

Answer: B - Hardware Abstraction Layer hides complexity.

Question 4

Which page replacement is optimal but impossible?

  • A) FIFO
  • B) LRU
  • C) OPT
  • D) Clock

Answer: C - OPT requires time travel!
